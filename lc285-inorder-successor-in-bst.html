LC 285 — Inorder Successor in BST

Algorithm

    

      
Walk from root while node != null:

      

        
• node.val > p.val:

        

          
- successor = node

          
- node = node.left

        

        
• else:

        

          
- node = node.right

        

      

      
Return successor.

    

    

      
Why remember + go left?

      

        If node.val > p.val, node is a successor candidate but maybe not the tightest. Going left searches for a smaller value that's still > p.val. If left subtree has nothing > p.val, we pivot right (Case 2) elsewhere and keep the current remembered node.
      

    

    

      
Why discard + go right?

      

        If node.val ≤ p.val, then node and its entire LEFT subtree are all ≤ p.val (BST invariant). None of them can be a strict successor. Only the right subtree might help.
      

    

    

      
LC 510 variant

      

        Given only p with a .parent pointer (no root): if p.right exists → leftmost of p.right; else walk up via parents until p is in the left subtree of its ancestor. Same two mental cases.
      

    

    

      
Family placement

      

        BST descent with running candidate. Same skeleton as LC 270 Closest BST Value (running best), LC 700 Search (no tracker), LC 235 LCA (split-point detect). Inorder version is O(n); descent is O(h).
